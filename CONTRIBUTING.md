# Contributing

## Setup

Install [uv](https://docs.astral.sh/uv/), then:

```sh
uv sync --all-groups
uv run prek install   # or pre-commit install
```

## Checks

The CI runs all of them, on Python 3.10 to 3.14:

```sh
uv run pytest --cov          # 100% of lines and branches
uv run ruff check . && uv run ruff format --check .
uv run mypy                  # strict
uv run pyright               # strict
uv run pyright --verifytypes mawaqit --ignoreexternal  # 100% typed API
```

## How the code is organized

Most of the code is generated from the OpenAPI description of the API, which
lives in the private [mawaqit/api-spec](https://github.com/mawaqit/api-spec)
repository.

| Path | Written by |
| --- | --- |
| `src/mawaqit/types.py` | The generator: the models, from the schemas. |
| `src/mawaqit/resources/` | The generator: one class per tag, one method per operation. |
| `src/mawaqit/_client.py` | The generator: the clients and their resources. |
| `tests/examples/` | The generator: real API responses, copied from the spec. |
| `src/mawaqit/_base_client.py` | Hand: requests, authentication, retries, errors. |
| `src/mawaqit/_exceptions.py`, `_models.py`, `hijri.py` | Hand. |
| `codegen/` | Hand: the generator and its templates. |

Generated files start with `# Generated by codegen/generate.py`: never edit
them, change the spec or the templates instead.

## Changing the API

1. Change the spec in mawaqit/api-spec and tag a new version.
2. Pin it here and regenerate the code. This needs the
   [GitHub CLI](https://cli.github.com), logged in with access to the spec:

   ```sh
   uv run --group codegen codegen/generate.py --pin v0.2.0
   ```

3. Add tests, and commit the generated files with `codegen/spec.json`.

`codegen/generate.py` alone regenerates the code from the pinned spec. The
`Codegen` workflow checks that the committed code matches it, reading the spec
with the `API_SPEC_DEPLOY_KEY` secret of the `api-spec` environment: a
read-only deploy key of mawaqit/api-spec.

## Releasing

1. Bump `src/mawaqit/_version.py` and move the changes of `CHANGELOG.md` under
   the new version.
2. Publish a GitHub release whose tag is the version, like `2.0.0`.

The `Release` workflow then runs the CI, and publishes to TestPyPI, then to
PyPI, with trusted publishing.
